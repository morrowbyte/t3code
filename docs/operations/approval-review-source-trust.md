# Host-bound approval orders

The host records the exact original task before forwarding it to a configured VM. The normal
chat composer offers **Host-bound task** independently of pending approvals. The host needs
no local model. An order can produce several proposals; each proposal requires its own frozen
package, human decision and single claim. Unknown forwarding or execution is never retried
automatically.

`T3CODE_APPROVAL_REVIEW_HOST_POLICY` explicitly qualifies source browser sessions and paired
VM channels. Its schema is in
[`ApprovalReviewOrderPolicy.ts`](../../apps/server/src/orchestration-v2/ApprovalReviewOrderPolicy.ts).
All lists default empty. Pairing alone, general `orchestration:operate`, `role=user`, a copied
order ID, or caller-supplied environment and thread IDs do not qualify a source. The configured
human ingress must itself be inaccessible to the requester. The UI's agent test browser must
use `sourceKind: synthetic` and `testOnly: true`; those orders cannot be accepted or claimed.

Each incoming VM channel pins a session, subject and DPoP proof-key thumbprint, with only
`approval-review:request`. The receiver separately pins the host principal and destination
thread. Production forwarding uses the existing Fleet HTTPS configuration and privately stored
P-256 transport key and credential. No signing key or credential is generated by the feature.
Literal loopback HTTP is supported only for explicitly synthetic development orders.

The host registry supplies the original text, immutable revision and acknowledged VM assignment
when assembling a proposal. `host-order:<orderId>` identifies that stored original; it is not a
message deep link. Review displays the exact excerpt and expandable full text from the bound
host authority. The source thread is context, not evidence of a separate timeline message.
Old signature receipts remain readable as legacy data and cannot authorize execution.

On the VM, `approval_review_order` exposes the assignment for the actual active provider run.
`approval_review_propose` uses that server-derived assignment and the provisioned DPoP callback;
the model does not supply an order, thread, source or run identity. A compromised guest can still
act on its own legitimate channel. Provenance verifies the order and request channel, not the
model's reasoning or the safety of its proposed code.

Before enabling real human orders, verify that guest-held Fleet, filesystem, terminal, management
and existing session credentials cannot modify the host registry, source policy, approver session
or transport stores. Storing them outside the VM alone does not establish this boundary. A guest
standard account also does not protect against a guest administrator. Preserve existing working
management connections; isolate the execution service and provision narrow channels separately.

Provision the host policy and the VM receiver/callback policy with
separate scoped sessions, fixed target identities and private-store references. The owner must
perform host setup and personally pair before any real package is generated. Keep execution
disabled until source/channel and worker isolation are verified. Rollback removes only those
feature policy entries and revokes the newly provisioned feature sessions; preserve original
profiles, keys and management sessions.

Local two-environment tests establish development transport and binding behavior only. They do
not establish human presence, actual VM isolation, real external execution or independent SSH
readback.
